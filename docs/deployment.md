# デプロイ手順：TaskManagement（AWS + Terraform）

このドキュメントは、本プロジェクトをAWS上にデプロイするための手順書です。
AWSマネジメントコンソールを手動で操作するのではなく、**Terraform（IaC）を使ってコードでインフラを構築**し、
**AWS CLIベースでの認証・操作**を前提にしています。AWS・Terraform・IaCが初めての人向けに、概念の解説も含めます。

## 0. 前提知識の解説

### AWSとは

AWS（Amazon Web Services）は、サーバー・データベース・ネットワークなどのITインフラを、
必要な分だけ・使った分だけの従量課金で借りられるクラウドサービスです。
物理的なサーバーを購入する代わりに、Web画面やAPI経由で「サーバーが欲しい」と申請すると、数分で使えるようになります。

このプロジェクトのデプロイで使う主なAWSサービスは以下の通りです。

| サービス | 役割 |
|---|---|
| EC2 (Elastic Compute Cloud) | 仮想サーバー。今回はこの上でDocker Composeを動かす |
| VPC (Virtual Private Cloud) | AWS上の仮想ネットワーク。EC2などをどのネットワークに置くか定義する |
| セキュリティグループ | EC2への通信を許可するポート・送信元を制御するファイアウォール |
| Elastic IP | EC2に割り当てる固定のグローバルIPアドレス |
| IAM (Identity and Access Management) | AWSアカウント内のユーザー・権限を管理する仕組み |

### IaC（Infrastructure as Code）とは

IaCとは、インフラの構成を「コード（設定ファイル）」として記述し、それを実行することでインフラを構築・変更する手法です。

AWSのマネジメントコンソール（Web画面）を手動でポチポチ操作して構築する方法（俗に「ClickOps」と呼ばれる）には、
以下のような問題があります。

- 何をどう設定したかの記録が残らず、属人化する
- 同じ環境をもう一度作るのが大変（再現性がない）
- 変更前に何が起きるか事前に確認できず、誤操作に気づきにくい
- Gitでのバージョン管理・PRでのレビューができない

IaCなら、このプロジェクトのアプリケーションコードと同じように、インフラの構成もGitで管理し、
プルリクエストでレビューし、変更前に差分を確認できます。

### Terraformとは

Terraformは、IaCを実現するための代表的なツール（HashiCorp社製）です。特定のクラウドに縛られず、
AWS・GCP・Azureなど様々なクラウドサービスを同じ書き方で操作できます。

主要な概念は以下の通りです。

| 用語 | 説明 |
|---|---|
| Provider（プロバイダー） | 操作対象のクラウド（今回はAWS）を扱うためのプラグイン |
| Resource（リソース） | 作成したいインフラの単位（例：EC2インスタンド1台、セキュリティグループ1つ） |
| `.tf`ファイル | 「あるべきインフラの状態」を宣言的に記述する設定ファイル |
| State（ステート） | 現在Terraformが作成・管理しているインフラの状態を記録したファイル（`terraform.tfstate`）。次回実行時にこれと`.tf`の差分を計算する |
| `terraform plan` | 現在の状態と`.tf`の内容を比較し、何が作成・変更・削除されるかを**事前にプレビュー**するコマンド。実際の変更は行わない |
| `terraform apply` | `plan`の内容をAWSに実際に反映するコマンド |
| `terraform destroy` | Terraformで作成したリソースをすべて削除するコマンド |

**重要**：`terraform.tfstate`には機密情報が含まれ得るため、Gitにコミットしません（`.gitignore`で除外します）。

### AWS CLIとは

AWS CLIは、AWSをコマンドラインから操作するためのツールです。Terraformを実行する際も、
内部的にはAWS CLIと同じ認証の仕組み（`~/.aws/credentials`に保存されたアクセスキー）を利用します。

## 1. デプロイするアーキテクチャ

学習の第一歩として、覚える概念を絞った最もシンプルな構成にします。ローカル開発環境（[技術スタック](tech-stack.md)参照）と
ほぼ同じ形で、EC2インスタンス1台の中でDocker Composeを動かします。

```
                    Internet
                        │
                  [Elastic IP]
                        │
        ┌───────────────────────────────┐
        │  EC2インスタンス（Ubuntu）      │
        │  ┌───────────────────────────┐│
        │  │ Docker Compose             ││
        │  │  ├─ backend  (Spring Boot) ││
        │  │  ├─ frontend (Vite build)  ││
        │  │  └─ db       (PostgreSQL)  ││
        │  └───────────────────────────┘│
        └───────────────────────────────┘
              ▲
              │ セキュリティグループ（22/80番ポートのみ許可）
```

- DBもコンテナとしてEC2内で動かし、RDS（マネージドDB）は使いません（コストと設定を最小化するため）
- 学習が進んだ段階で、ECS Fargate + RDS + S3/CloudFrontといった、より実務に近いサーバーレス構成へのステップアップも検討できます

### 想定コスト

- EC2は無料利用枠対象の`t2.micro`または`t3.micro`を使えば、アカウント作成から12ヶ月は無料枠内に収まる想定です
- 無料枠を超えた場合、あるいは12ヶ月経過後は、月あたり概ね$5〜10程度が目安です（リージョン・稼働時間による）
- **使わない期間は`terraform destroy`でリソースを削除すれば課金は止まります**

## 2. 事前準備（ユーザー自身が行う作業）

ここから先は、AWS上の重要な認証情報に関わるため、Claude Codeが代行することはできません。
以下の手順を実際にご自身で行ってください。

### 2-1. AWSアカウントの作成

1. https://aws.amazon.com/jp/ の「無料アカウントを作成」から作成する
2. メールアドレス・パスワード・クレジットカード情報の登録が必要（本人確認のため）
3. 作成直後にログインできるのは「ルートユーザー」のみ

### 2-2. ルートユーザーにMFA（多要素認証）を設定する

ルートユーザーはアカウント内で最も強い権限を持ち、漏洩すると被害が甚大なため、必ずMFAを設定してください。

1. マネジメントコンソールにルートユーザーでログイン
2. 右上のアカウント名 → 「セキュリティ認証情報」
3. 「多要素認証（MFA）」→ 「MFAデバイスの割り当て」
4. スマートフォンの認証アプリ（Google Authenticator、Authyなど）を使って設定する

### 2-3. 予算アラートを設定する（強く推奨）

想定外の課金に気づけるよう、必ず最初に設定してください。

1. マネジメントコンソールで「Billing and Cost Management」を開く
2. 「予算（Budgets）」→「予算を作成」
3. 例えば「月額$10を超えたらメール通知」のような予算を作成する

### 2-4. IAMユーザーを作成する（Terraform/AWS CLI用）

**ルートユーザーの認証情報を日常作業やTerraformで使うことは絶対に避けてください。** 権限を持ったIAMユーザーを別途作成します。

1. マネジメントコンソールで「IAM」を開く
2. 「ユーザー」→「ユーザーを作成」
3. ユーザー名を入力（例：`terraform-deploy`）。「AWSマネジメントコンソールへのユーザーアクセスを提供する」はチェックしない（プログラムからの利用のみのため）
4. 許可の設定で、学習目的のため簡単さを優先し `AdministratorAccess` ポリシーを直接アタッチする
   - 本来は必要な操作（EC2・VPC・IAMロード作成など）に絞ったポリシーを設計するのが望ましいですが、最初の学習ステップとしては簡略化しています
5. 作成後、そのユーザーの詳細画面 →「セキュリティ認証情報」タブ →「アクセスキーを作成」
6. ユースケースは「コマンドラインインターフェイス (CLI)」を選択
7. 表示された**アクセスキーID**と**シークレットアクセスキー**を安全な場所に控える（シークレットアクセスキーはこの画面でしか表示されません）

## 3. ローカルマシンのセットアップ

ここからはコマンドライン作業です。Claude Codeと一緒に進められます。

### 3-1. AWS CLIのインストール

```bash
brew install awscli
aws --version
```

### 3-2. 認証情報の設定

```bash
aws configure
```

以下を順に入力します。

- `AWS Access Key ID`：手順2-4で控えたアクセスキーID
- `AWS Secret Access Key`：手順2-4で控えたシークレットアクセスキー
- `Default region name`：`ap-northeast-1`（東京リージョン）
- `Default output format`：`json`

これらは `~/.aws/credentials` と `~/.aws/config` に保存されます（Gitとは無関係のホームディレクトリ配下です）。

### 3-3. 動作確認

```bash
aws sts get-caller-identity
```

自分のアカウントID・IAMユーザーのARNが表示されれば認証成功です。

### 3-4. Terraformのインストール

```bash
brew install terraform
terraform version
```

## 4. Terraformプロジェクトの準備

1. リポジトリ直下に `infra/`（または`terraform/`）ディレクトリを作成し、そこにTerraformコード（`.tf`ファイル）を配置する
2. `terraform.tfstate`・`*.tfvars`（認証情報や環境固有の値を書くファイル）を`.gitignore`に追加する
3. まずは**ローカルでstateを管理**します（学習目的のため）。チーム開発する場合はS3+DynamoDBでのリモートstate管理が定石ですが、これは将来のステップとします

## 5. 次のステップ

上記の準備（AWSアカウント・IAMユーザー・AWS CLI・Terraformのセットアップ）が完了したら、次のステップとして
Claude Codeと一緒に以下を行います。

1. VPC・サブネット・セキュリティグループをTerraformコードとして定義する
2. EC2インスタンスを定義する（起動時にDocker/Docker Composeを自動インストールする設定を含む）
3. Elastic IPを割り当てる
4. アプリケーションコードをEC2に反映する方法を決める（例：EC2上でリポジトリをgit cloneしてdocker compose up -d）
5. `terraform plan`で内容を確認し、`terraform apply`で実際に構築する

## 6. 安全に使うための運用ルール

- `terraform apply`（作成・変更）・`terraform destroy`（削除）は、実行前に必ず`terraform plan`の内容を確認し、
  Claude Codeから実行可否を確認します。自動では実行しません
- アクセスキーやシークレットアクセスキーは、`.tfvars`や環境変数など**Gitにコミットされない場所**にのみ保存します
- 使い終わったら`terraform destroy`でリソースを削除し、不要な課金を防ぎます
- 学習目的のアプリのため、常時稼働させ続ける必要はありません

## 7. 用語集

| 用語 | 意味 |
|---|---|
| リージョン | AWSのデータセンターがある地理的な場所の単位（例：東京は`ap-northeast-1`） |
| アベイラビリティゾーン（AZ） | リージョン内の独立したデータセンター群。障害分離の単位 |
| IAM | AWSアカウント内のユーザー・権限を管理する仕組み |
| アクセスキー / シークレットアクセスキー | IAMユーザーがプログラム（CLIやTerraform）からAWSを操作するための認証情報の組 |
| MFA（多要素認証） | パスワードに加えてスマホの認証コードなどでログインを保護する仕組み |
| VPC | AWS上に作る仮想的な専用ネットワーク |
| セキュリティグループ | EC2などへの通信を許可・拒否するファイアウォールルール |
| Elastic IP | 固定のグローバルIPアドレス。EC2を再起動してもIPが変わらないようにする |
| プロビジョニング | インフラ（サーバーなど）を実際に作成・準備すること |
